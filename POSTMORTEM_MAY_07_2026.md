# Разбор инцидента: задержки API и предотвращение каскадных сбоев

**Статус:** РЕШЕНО  
**Дата происшествия:** 7 мая 2026 г.  
**Серьезность:** Критическая (P1)  
**Местоположение:** Базовый кластер API

## 1. Краткое описание
Обнаружено критическое снижение производительности API из-за высокой задержки внешнего сервиса, к которому он обращается. Паттерн **предохранителя (Circuit Breaker)** позволил системе перейти от сбоев к самовосстановлению, предотвратить полное исчерпание ресурсов и сохранить минимальную доступность сервиса за счёт резервного режима.

## 2. Хронология инцидента
* **09:32:** Мониторинг обнаружил первую задержку в 2000 мс при вызовах внешних служб.
* **09:34:** `STRIKE_COUNT` достиг порога (3 последовательных сбоя).
* **09:35:** сработало **КРИТИЧЕСКОЕ ПРЕДУПРЕЖДЕНИЕ**. Состояние предохранителя изменилось на `OPEN`.
* **09:36:** Автоматическая проверка восстановления: API начал обслуживать немедленные ответы `timeout_fallback`, сократив задержку с 2000 мс до <200 мс.

## 3. Анализ первопричин (5 «почему»)
1. **Почему API работал медленно?** Основной поток был заблокирован в ожидании ответов внешней службы.
2. **Почему возникла блокировка?** На сетевом уровне не были заданы обязательные тайм-ауты для вызовов зависимых сервисов.
3. **Почему не произошел сброс нагрузки?** В системе отсутствовал механизм автоматического обнаружения сбоев.
4. **Почему мы пропустили обнаружение раньше?** Бюджеты ошибок не были определены для последовательных сбоев.
5. **Основная причина:** Отсутствие архитектурного шаблона **Предохранитель**, что приводит к каскадному увеличению задержки в основном кластере.

## 4. Меры по устранению причин инцидента
- [x] Реализовать `Correlation-ID` для сквозного отслеживания запросов.
- [x] Настроить **оповещения, требующие действий**, по последовательностям ошибок (3/3).
- [x] Внедрить автоматический **предохранитель**: при превышении порога переходить в состояние `CIRCUIT_OPEN`.
- [ ] **Следующий шаг:** Реализовать состояние `Half-Open` для автоматической проверки сервиса и восстановления.

## 5. Извлеченные уроки
Статического мониторинга недостаточно для высокодоступных кластеров. В основной инфраструктуре необходимы **паттерны устойчивости**, включая Circuit Breaker, чтобы быстро прекращать заведомо неуспешные операции и защищать ресурсы системы от проблем внешних зависимостей.
